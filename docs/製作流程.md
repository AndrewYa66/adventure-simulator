# 製作流程 v1.0

> 狀態：2026-11-20 與 Andrew 確認定稿。
> 適用範圍：`docs/PROJECT_GOALS.md` 裡的每一個 O 項目（或其中一個階段），以下稱「模組」。只用於程式模組；劇情寫作之後另外設計較輕的版本。

## 總覽

```
決策(grill-me) → 決策 pre-mortem → 【就緒檢查】
→ 製作 → 製作 pre-mortem
→ Review 1（另開 thread）→ 修正 1
→ Review 2（同一個 review thread）→ 修正 2
→ 測試 → 完成
```

Andrew 需要出現的點只有三個：決策階段、決策 pre-mortem 的風險取捨、測試階段的手感與視覺。其他階段在規格寫清楚的前提下全自動跑。

## 1. 決策（grill-me）

- Claude 讀完相關文件與程式後，列出這個模組所有需要決定的問題，先給全貌清單。
- 一批 3～5 題，每題附 Claude 的建議與理由；Andrew 可以回「照建議」或只改其中幾題。
- 答案會引出新問題，持續追問到「製作時不需要再問任何人」為止。
- 產出：模組規格書 `docs/specs/<模組>.md`（例如 `docs/specs/O34-2.md`），格式見文末「規格書範本」。PROJECT_GOALS.md 只保留索引、狀態與已確認決策摘要，製作與 review 都只讀規格書。

## 2. 決策 pre-mortem

- 假設：「這個模組上線兩週後被判定失敗，為什麼？」列出 5～10 個失敗原因。
- 每個原因只能有三種處理：變成一個新決策、變成一條驗收測試、或明確接受風險。
- Andrew 確認處理方式後，進入就緒檢查。

### 就緒檢查（Definition of Ready）

全部打勾才能開工：
- [ ] 範圍內／範圍外都列清楚，延後項目已寫進 PROJECT_GOALS
- [ ] 所有會改變玩家可見行為、存檔格式、資料格式、AI 回應格式的決策都已定
- [ ] 每條驗收條件都能用 build／lint／test:sim／Playwright／test:ai 其中一種驗證
- [ ] 數值類問題有預設值，並標記為「可調」
- [ ] 「自主權限」段落寫好：哪些可以自己決定、哪些必須停下來問

## 3. 製作

- 開工時從 main 開一個模組分支（例如 `module/O34-2`），所有提交都在這個分支上。
- 只依規格書製作；規格沒寫到的實作細節自行決定，記在規格書的「製作紀錄」。
- 碰到會改變已確認決策的情況：停下來問，不自行改規格。
- 完成後跑 build、lint、引擎與劇本分離檢查。

## 4. 製作 pre-mortem

- 假設：「review 抓到嚴重問題」或「玩家第一次玩就壞了」，最可能是什麼？
- 能當場修的先修；修不了的寫進交接單給 review。

## 5. Review（另開 thread）

- review thread 只讀規格書、diff 和交接單，不讀製作過程的對話，避免被製作者的想法帶走。
- review thread 由製作 thread 請 coordinator 另開。
- 只寫意見，不改程式。每條意見分級：阻擋／應修／建議。
- 第二輪 review 在同一個 review thread，只檢查上一輪意見有沒有解決，以及修正有沒有引入新問題。

## 6. 修正

- 回到製作 thread 修正。阻擋與應修必須處理；建議類可以拒絕，但要寫理由。
- 若 review 意見和規格書衝突：不修，交給 Andrew 決定。
- 第二輪修正後仍有阻擋問題：不跑第三輪，整理成選項交給 Andrew 決定。

## 7. 測試

- Claude 跑：build、lint、test:sim、Playwright 無頭測試、test:ai（先說要打幾次）。
- Andrew 只看手感與視覺。
- 通過後更新 PROJECT_GOALS 狀態，把模組分支合併回 main。

## 規格書範本

```
# <模組> 規格書
## 目標（一句話）
## 範圍內 / 範圍外 / 延後
## 已確認決策（每條：決策、理由）
## 資料與介面變更（型別、存檔版本、AI 回應格式、content 範本）
## 驗收條件（每條標明驗證方式）
## 自主權限
- 可自行決定：
- 必須停下來問：
## Pre-mortem 風險與處理
## 製作紀錄（製作階段填）
## Review 紀錄（review 階段填）
```

## 通用 review 檢查清單

每個模組的 review 都要逐項檢查以下各點，再檢查規格書的「驗收條件」。規格書的驗收條件只寫這個模組特有的部分，通用項目不必重寫。

### 規格一致
- [ ] 規格書「範圍內」每一項都有實作，「範圍外」沒有偷做
- [ ] 每條驗收條件都有實際跑過的證據（指令輸出、截圖、test:ai 次數與結果）
- [ ] 製作紀錄寫明了自行決定的實作細節；沒有未經同意就改變已確認決策

### 架構原則
- [ ] 引擎與劇本分離：`src/`（不含 `src/data/`）沒有具體內容 ID 或名稱，包含註解
- [ ] 狀態只由規則改變：AI 只能提議，前端驗證後才套用；沒有新的「AI 直接改狀態」路徑
- [ ] 同一個動作只有一個執行函式（選項、打字、HUD 都呼叫它）
- [ ] 數值放在資料檔並標「可調」，不寫死在程式裡

### 資料與相容
- [ ] 改了存檔格式就把 `SAVE_SCHEMA_VERSION` 加一
- [ ] 改了 AI 回應格式就把 `formatVersion` 加一，同步更新解析與 schema
- [ ] 改了 API 或資料格式就同步更新 `docs/API.md`、型別與 `validate:data`

### AI 成本與穩定
- [ ] 每回合 AI 呼叫次數沒有超過已確認的上限
- [ ] 系統提示沒有超過 20,000 字元的預算
- [ ] AI 回應格式錯誤、缺欄位、給非法 ID 時有明確的處理，不會讓遊戲卡住

### 玩家體驗
- [ ] 死亡、昏迷、戰鬥中、時間線結束時，新功能的按鈕和輸入都正確停用
- [ ] 系統訊息用繁體中文，告訴玩家發生了什麼、接下來能做什麼
- [ ] 手機寬度可操作

### 驗證
- [ ] `npm run build`、`npm run lint` 通過
- [ ] 動到主線或劇本規則時有跑 `test:sim`
- [ ] 動到 AI 回應或上下文時有跑 `test:ai`，並記錄呼叫次數

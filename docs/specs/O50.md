# O50 互動選項化 規格書

> 狀態：決策完成、就緒檢查通過（2026-11-20）。製作分三階段：`module/O50-1`、`module/O50-2`、`module/O50-3`。
> 吸收 O8（提供符合區域與情境的 AI 對話選項）。討論紀錄見專案檔案 `design/互動形式討論.md`。

## 目標（一句話）

把主要互動從「自由輸入＋HUD 按鈕兩套並行」改成「故事下方一條由規則產生的選項列為主、自由輸入為輔」，所有動作共用同一套執行函式與檢定規則。

## 選項的三層

| 層 | 誰產生 | 例子 | 執行 |
| --- | --- | --- | --- |
| 系統選項 | 前端依狀態產生 | 前往綠林古道、打開商店、交付任務、挑戰、等待 | 規則直接執行 |
| 情境選項 | AI 從行動類型白名單挑選，規則審核 | `[魅力 13] 說服守衛放行` | AI 一次寫好成功／失敗敘事，規則擲骰並套用 |
| 劇本選項 | 寫在劇情片段的 `choices` | 追問村長「以前」的意思／拒絕 | 規則判斷條件、擲骰、設旗標，AI 只敘事 |

自由輸入保留在選項列最後（「其他行動…」），只在戰鬥中與劇本關鍵抉擇時停用。

## 第一階段（O50-1）：系統選項與選項列

### 範圍內
- 選項列元件：固定在輸入框上方、不隨訊息捲動；只有最新一則訊息的選項可以按。
- 系統選項由規則依目前狀態產生，每次狀態改變後重算，不存入存檔。
- 分組：「移動 ▸」「人物 ▸」（在場人物：交談、挑戰）「任務 ▸」（接取、交付）「設施 ▸」（商店、旅店、告示板）「等待」。點了才展開該組。
- 當下可做的事直接列在最前面、不需展開：可交付的任務、剛遭遇的敵人。
- 商店在選項列只放「打開商店」，點了展開商品清單（買、賣、服務），使用現有規則。
- HUD 移除動作按鈕（前往、挑戰、接取任務、交付、購買、出售、使用服務、戰鬥按鈕），只留狀態、背包（含使用、裝備）、技能、勢力、存檔。
- 戰鬥中：攻擊、技能、逃跑移到選項列，戰鬥規則不變；輸入框維持停用。
- 執行後的回饋：移動、交談、開始戰鬥接一次 AI 敘事（移動沿用 O44「先移動再敘事」）；買賣、裝備、用道具、等待只顯示系統訊息、不呼叫 AI。
- 「交談」選項：送一則固定格式的玩家行動給 AI（例如「與某人交談」），走一般回合流程。
- 「技能 ▸」分組（2026-11-20 Andrew 確認）：戰鬥外可用的技能（目前為治療類）。HUD 的治療技能按鈕移除後需要入口，因此列入選項列。
- 打字的系統動作：現有正規表示式（道具、攻擊、等待、技能、移動）保留，但改為呼叫與系統選項相同的執行函式。
- AI 回應格式不變；`suggestedActions` 照樣顯示在系統選項之後（第二階段才換掉）。

### 範圍外
- 情境選項、門檻、劣勢（第二階段）。
- 劇本選項（第三階段）。
- 點擊擲骰（O48）、HUD 圖示分頁（O49）。

## 第二階段（O50-2）：情境選項與門檻

### 範圍內
- 行動類型白名單（資料檔，例如 `src/data/action_types.json`）：

| 類型 | 能力值 | 未達門檻時 |
| --- | --- | --- |
| 交談、詢問 | 不檢定 | — |
| 說服、欺瞞 | 魅力 | 鎖定顯示 |
| 威嚇 | 魅力或力量（擇高） | 鎖定顯示 |
| 觀察 | 感知或智力（擇高） | **隱藏** |
| 調查、回想知識 | 智力 | 鎖定顯示 |
| 潛行、巧手 | 敏捷 | 鎖定顯示 |
| 強行 | 力量 | 鎖定顯示 |
| 忍耐 | 體質 | 鎖定顯示 |

  欄位至少有：`id`、`label`、`abilities`（一或兩項，擇高）、`hiddenBelowThreshold`。

- 難度表（資料檔，全部可調，O46 後校準）：

| 難度 | DC | 門檻（能力值） |
| --- | --- | --- |
| 簡單 | 8 | 無 |
| 普通 | 11 | 無 |
| 困難 | 14 | 13 |
| 極難 | 17 | 15 |

- AI 回應格式第 6 版：
  - `suggestedActions` 改為 `situationOptions: [{ label, actionType, difficulty, targetUnitId? }]`。
  - `checkRequest` 改為 `{ actionType, difficulty, reason }`，DC 與能力值由規則決定。
  - `checkOutcomes`（成功／失敗敘事）照舊，一次寫好。
- 情境選項規則：每回合最多 3 個，其中鎖定最多 1 個；系統選項不計。前端過濾不合法的類型、難度、目標；過濾後超過上限時捨棄多餘的。
- 門檻：能力值低於門檻時，選項鎖定（點不了，標示需求，例如 `🔒 [魅力 13] 說服守衛`）；觀察類隱藏。達標後選了仍擲 d20。
- 自由輸入：AI 把玩家文字對應到白名單中的一種類型，用 `checkRequest` 回報。
  - 對應到需要檢定的類型：照常擲骰。
  - 玩家未達該難度的門檻：仍擲骰，但有**劣勢**（擲兩顆 d20 取低）。
  - 對應不到任何類型：視為純敘事，不改變狀態，耗時 10 分鐘（沿用對話規則）。
- 多能力值：同一目標可用多個情境選項提供不同能力值的解法（例如撞門／撬鎖）；兩項擇高由白名單欄位決定。
- 重試冷卻（pre-mortem 第 3 項）：同一目標、同一行動類型失敗後，經過 1 遊戲小時或離開地區前不能再試；選項顯示「已嘗試」，打字重試時以系統訊息擋下、不呼叫 AI。冷卻紀錄存入存檔。
- 刪除第一階段保留的正規表示式中 AI 能處理的部分，只留需要精確數字的解析（等待時長、自傷數值）與道具、技能名稱的直接比對。
- 提示詞附上各難度的範例情境，避免難度一律給「普通」。

### 範圍外
- 多階段檢定（第三階段，只限劇本）。
- 擲骰動畫與點擊擲骰（O48）。

## 第三階段（O50-3）：劇本關鍵抉擇

### 範圍內
- 劇情片段新增 `choices`（取代純文字的 `scene.playerChoices`，後者保留給一般場景參考）：

```json
"choices": [
  { "id": "ask", "label": "追問「以前」是什麼意思",
    "requires": { "flags": [], "ability": null },
    "check": { "actionType": "說服", "difficulty": "困難" },
    "onSuccess": { "setFlags": ["..."], "eventIds": [] },
    "onFailure": {} },
  { "id": "refuse", "label": "拒絕委託",
    "onChoose": { "setFlags": ["..."] } }
]
```

  `check` 也可以是多階段 `steps: [{ actionType, difficulty, onFailure }]`，依序擲，任何一關失敗即走該關的 `onFailure`。
- 關鍵抉擇出現時：鎖住自由輸入與所有系統選項，只能看背包、狀態、存檔；選完立即自動存檔。抉擇可標 `deferrable: true`（預設 false），可延後時不鎖。
- AI 只負責敘事；條件、擲骰、效果由規則處理。
- 格式寫入 `docs/CONTENT_GUIDE.md`，`validate:data` 檢查：行動類型與難度合法、旗標有登記來源、`id` 不重複。
- 範例：把現有「村長的隱憂」的兩個 playerChoices 改寫為 `choices`。

### 範圍外 / 延後
- 寫手用 Markdown 範本撰寫 choices（等 O36）。
- 新劇本的關鍵抉擇（奪取、強制事件等，等寫手與 O41）。

## 已確認決策（2026-11-20）

| 決策 | 理由 |
| --- | --- |
| 系統操作全部交給前端 | 規則早已決定結果，經過 AI 只增加成本與不一致 |
| 三層選項；自由輸入保留但限制「能做什麼」，不限制「何時能用」 | 選項減負，自由輸入保留驚喜；只在特殊情境開放會讓玩家放棄嘗試 |
| HUD 移除動作按鈕 | 避免兩套操作並存 |
| 移動、交談、開戰接 AI 敘事；其餘只顯示系統訊息 | 控制 AI 呼叫數 |
| AI 只選難度等級，規則換算 DC 與門檻 | AI 自訂 DC 不穩定 |
| 門檻決定能不能點，點了仍擲骰；打字可擲但有劣勢 | 保留能力值的意義，也保留靠運氣的空間 |
| 只有觀察類隱藏 | 鎖定顯示讓玩家知道培養能力值有用；祕密類隱藏保留驚喜 |
| 每回合情境選項 ≤ 3、鎖定 ≤ 1 | 避免選項過多或一直提醒「做不到」 |
| 選項不存檔，每次重算 | 永遠與狀態一致 |
| 純敘事輸入耗時 10 分鐘 | 防止無限拖延，維持戰況壓力 |
| 打字失敗後同目標同類型冷卻 1 遊戲小時或離開地區 | 防止以劣勢無限重試繞過門檻 |
| 一份規格書、三個分支 | 決策一次定完，製作與 review 分階段 |

## 驗收條件

先逐項通過 `製作流程.md` 的「通用 review 檢查清單」，再檢查以下各條。

### 第一階段
1. 每種系統動作（移動、交談、挑戰、接取、交付、打開商店、等待、戰鬥中的攻擊／技能／逃跑）都能從選項列執行，結果與原 HUD 按鈕相同。— Playwright
2. HUD 沒有任何動作按鈕（背包的使用、裝備除外）。— Playwright
3. 不合法的動作不會出現：未接任務不顯示交付、前置任務未完成的地點不可前往、安全地區不顯示挑戰野外敵人。— Playwright
4. 狀態改變後（移動、交付、戰鬥結束）選項立即更新；舊訊息的選項不能按。— Playwright
5. 買賣、裝備、等待不呼叫 AI。— Playwright 監聽網路請求
6. 打「攻擊某某」與按「挑戰」走同一個函式、結果一致。— 暫時 Node 腳本或 Playwright
7. 寬度 375px 時，選項列收合後不超過兩行，且不隨訊息捲動。— Playwright 截圖
8. 死亡、昏迷、時間線結束時選項列停用；戰鬥中昏迷時只剩跳過回合。— Playwright
9. test:ai「移動」分組回歸通過（約 5 次）。— test:ai

### 第二階段
10. 不合法的情境選項（類型不存在、難度不存在、目標不在場）被過濾；過濾後超過上限時只留 3 個、鎖定 ≤ 1。— 暫時 Node 腳本
11. 能力值低於門檻：一般類型顯示鎖定並標需求、不能點；觀察類不顯示。— Playwright（改存檔能力值）
12. 打字對應到未達門檻的類型時以劣勢擲骰，結果卡片顯示兩顆骰；達標時只擲一顆。— 暫時 Node 腳本＋Playwright
13. 對應不到類型的純敘事不改變狀態、耗時 10 分鐘。— Playwright
14. 失敗後同目標同類型在冷卻內不能再試、不呼叫 AI；1 遊戲小時後或離開地區可再試；冷卻存讀檔後保留。— 暫時 Node 腳本
15. test:ai「情境選項」分組約 12 次：合法率 ≥ 11/12；明顯困難的情境 AI 給困難以上；敘事不宣稱未套用的物品或旗標。— test:ai
16. 每回合 AI 呼叫數未增加。— Playwright 監聽網路請求

### 第三階段
17. 「村長的隱憂」以 `choices` 呈現兩個選項；追問需擲骰，成功與失敗分別設定對應旗標；拒絕直接設旗標。— Playwright
18. 抉擇待決時自由輸入與系統選項停用，背包、狀態、存檔可看；選完自動存檔，讀檔不會回到抉擇前。— Playwright
19. `validate:data` 能抓到不合法的行動類型、難度、未登記旗標、重複 id。— 故意寫錯的暫時資料
20. test:ai「主線」相關分組約 5 次通過。— test:ai

## 製作紀錄（製作階段填）

### 第一階段（O50-1，分支 `module/O50-1`，2026-11-20）

自行決定的實作細節：
- 結構：`src/utils/systemOptions.ts`（選項產生、開戰條件 `getCombatStartBlock`）、`src/components/OptionBar.tsx`（選項列）、`App.tsx` 的 `runSystemAction` 分派到各執行函式（`executeTravel`、`executeTalk`、`executeStartCombat`、`executeWait` 與原有的接取、交付、買賣、服務、技能、道具、攻擊、逃跑處理）。`tradeRules.canTrade` 改為匯出供選項共用。
- 收合列：一行系統選項（當下可做的事在前，再接分組）＋一行 AI 建議行動，兩行都不換行、橫向捲動，保證收合時不超過兩行。展開面板在兩行上方，最高 38vh、可捲動。
- 「任務 ▸」同時列交付與接取；可交付的任務另外直接列在收合列最前面。
- 「人物 ▸」：在場且存活的地區居民，加上目前已遭遇的單位；每人一個「交談」，可開戰者另有「挑戰」（剛遭遇的敵人的挑戰只放在最前面，不重複）。挑戰只對敵對單位；打字攻擊非敵對人物仍會激怒對方（沿用原規則）。
- 「設施 ▸」：每間可交易的商店一個「打開某店」（有服務的商店以 🛏️ 表示旅店），有告示板的地點加「查看告示板」。打開後的清單順序：服務、購買、出售；商店內連續買賣時面板保持展開，其他動作執行後收合。金幣或庫存不足、生命魔力已滿時商品／服務列出但停用並標原因（展開清單才看得到；2026-11-20 Andrew 確認維持此做法）。
- 「查看告示板」展開此地可接取的委託（與「任務 ▸」的接取相同），不呼叫 AI。2026-11-20 Andrew 確認維持不呼叫 AI、不改已確認決策；告示板保底劇情片段的觸發留到第三階段處理。
- 新增「技能 ▸」分組（原規格的分組清單沒有，2026-11-20 Andrew 確認保留並補入範圍內）：戰鬥外的治療技能原本是 HUD 按鈕，移除後需要入口；生命已滿時不列出。HUD 改為唯讀的「✨ 技能」清單。
- 「等待 ▸」：時長放在 `scenario.json` 的 `rules.waitOptionMinutes`（預設 1、2、4、8 小時，可調），`validate:data` 檢查 1～480 分鐘。
- 開戰敘事：開戰由規則完成後送一次 AI，以 `sendPlayerAction` 新增的 `turnNote` 說明「只描述開場、不提出狀態變更」，只採用 `storyText`。敘事期間選項列停用（busy），失敗時顯示錯誤、戰鬥照常進行。未設定 AI 時略過敘事。
- 移動：選項列、打字的明確移動、候選目的地按鈕都走 `executeTravel`（規則先移動，再接一次 AI 敘事）。未設定 AI 時只顯示移動結果（原本 HUD 移動不需 AI，保留此行為）；因此打字的明確移動在未設定 AI 時也會直接移動（原本會開啟金鑰設定視窗）。打字移動在規則無法移動時照舊交給一般 AI 回合。AI 失敗（網路、額度、HTTP 錯誤）時，已結算的移動與途中遭遇照常套用，只顯示「敘事失敗，移動已完成」（Review 第一輪 R1）。

- 「只有最新一則訊息的選項可以按」的判定：最新一則帶建議或候選目的地、且之後沒有玩家訊息的訊息；其選項移到選項列，其他訊息的選項以停用狀態留在紀錄中。系統訊息（例如世界變化、買賣結果）不會讓 AI 的建議失效。

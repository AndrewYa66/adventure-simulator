# 專案任務目標

## 專案願景

打造一款可在瀏覽器遊玩的繁體中文文字冒險遊戲，由玩家選擇的生成式 AI 擔任遊戲主持人，結合可追蹤的玩家存檔與靜態遊戲資料，讓玩家能持續探索、接任務、戰鬥並成長。

## 目前範圍

- React + TypeScript 前端，使用 Vite 建置並部署為靜態網站。
- 玩家可選擇 Google Gemini 或 OpenAI 模型；目前由瀏覽器直接呼叫所選服務。
- 遊戲資料以 JSON 隨前端部署；玩家狀態以 `localStorage` 保存。
- 遊戲回合由玩家行動、GM 敘事、建議行動和可選狀態變更組成。

## 已確認的設計決策（2026-10-05）

以下決策適用於 O28 之後的所有實作；變更前需先更新本節。

### 世界觀與故事

- **世界觀**：受托爾金啟發的原創奇幻世界，不直接使用《魔戒》的國家、地名與專有名稱（避免公開部署時的版權與商標問題）。種族與勢力見 `content/lore/` 的 RACE、FAC 條目。
- **故事藍本**（2026-10-06 改為寫手新大綱，見 `content/lore/LORE-003 主線大綱`）：人類只剩兩成土地，其餘由魔族與魔獸佔據。表面主線是人造勇者打倒魔王；暗線是王國與邪教徒以勇者為通道，餵養吞噬靈魂的人造神（最終頭目）。魔王其實是世界選出的當代勇者。原《星鐵亂世》設定停用，相關條目待改寫。
- **主角**：王國製造的人造勇者，本人不知情，身上帶有刻印；職業與陣營傾向由玩家選擇。
- **主線**（寫手大綱 V0.0，草案）：第一幕接受任命、組隊（王國指派 1 位同伴，自己找 1～2 位）、第一次奪取；第二幕深入魔族領地、刻印失效的強制事件、與魔王決戰（殺死、奪取或聯手）；第三幕真相揭露、人造神的倒數、選邊、最終戰。結局：1 期限內擊敗最終頭目（分支：靈魂值達門檻且奪取魔王成功時可取代人造神，檢定決定成神或被吞噬）、2 期限耗盡人造神完成、3 協助完成人造神計畫；變化軸為魔王的下場 × 靈魂值。細節見 LORE-003、ACT-1～3；期限從何時倒數、強制事件形式、地理與勢力仍待設計。
- **職階**：戰鬥、社會、生活三類共 24 種，見 `content/03 職階清單.md`。

### 第一版規模

- 3 幕、5～8 張地圖、10～15 個重要角色、2～3 位同伴。

## 任務目標與驗收條件

### P0 — 建立可靠的冒險回合

- 玩家能設定 API Key、送出自由輸入行動並收到 GM 回應。
- AI 回應能按 `AIResponsePayload` 契約解析；解析失敗時顯示可理解的備援訊息，不讓介面崩潰。
- HP、MP、經驗、金幣、道具、地圖與劇情旗標只依有效狀態變更更新。
- 結果不確定且失敗有影響的行動使用前端 d20 檢定；成功/失敗分支由檢定結果選擇，AI 負責敘事。
- 503 或網路暫時錯誤時會有限次重試；429 額度錯誤依種類處理（每日／帳戶額度用完不重試並提示恢復時間，每分鐘額度僅在短暫等待時重試一次）；最後失敗會顯示錯誤且解除載入狀態。

### P0 — 保護並維持玩家存檔

- 新玩家能建立有效的預設角色狀態。
- 玩家狀態修改後可保存，重新載入頁面仍能恢復。
- 無效或舊版存檔不會令遊戲初始化失敗；需提供安全回復預設存檔的方式。
- 開發階段（2026-10-05 決議）：存檔帶 `schemaVersion`，每次變更存檔格式就加一；版本不符的存檔直接捨棄並重新建立角色，不撰寫舊格式遷移。正式上線後才開始為舊版本提供遷移。
- 玩家可清除或重設存檔，且操作結果清楚可見。

### P1 — 完成核心遊戲資料循環

- 靜態 JSON 中的物品、地圖、怪物、等級和任務均具唯一 ID，並能互相正確參照。
- 玩家可取得、移除及檢視背包道具；數量不為負值，無效 item ID 不會污染存檔。
- 玩家可接取/完成任務並持續保存任務狀態。
- 地圖移動限制在有效連通地圖，顯示目前位置及可探索地點。

### P1 — 讓進度可玩且可理解

- 經驗累積與升級門檻依 `level_benchmarks.json`（同等級強度基準表）處理，升級會套用種族 × 職階 × 等級的數值成長。
- 戰鬥結果依明確遊戲規則結算，AI 敘事不能任意繞過核心數值限制。
- 對話紀錄能保留足以延續遊戲的劇情摘要，避免只依賴短期訊息或無限制累加上下文。
- 玩家能辨識建議行動、載入中、API 錯誤及存檔狀態。

### P2 — 發佈品質與維護性

- API/資料格式變更同步更新文件與型別。
- 建置與 lint 可成功，GitHub Pages 部署後主要遊戲流程可使用。
- 文件說明設定方式、API Key 儲存位置、存檔位置和已知限制。
- 評估是否引入後端代理以避免 API Key 暴露於使用者瀏覽器；若維持純前端，需清楚告知玩家此安全界線。

## 預計優化目標

以下項目按模組逐步實作；已完成項目會保留驗收條件供維護。

### O1 — 可收合的遊戲選單

狀態：已實作。

- 讓側邊選單可由玩家展開或隱藏，收合後仍保留清楚的重新開啟入口。
- 驗收：選單開合不遮住主要劇情和行動輸入；窄螢幕也能使用。

### O2 — 由遊戲資料約束任務與獎勵

狀態：已實作獎勵上下限，並限制 AI 直接增發經驗、金幣、道具或擊敗進度。

- 任務目標、可接受進度、獎勵種類與數量由遊戲資料或規則設定提供有效範圍及上限。
- AI 可協助敘述任務或在已定義選項內提出內容，但不能自行提高獎勵、建立超出限制的目標或直接判定未達成條件的任務完成。
- 驗收：任務及獎勵經前端規則驗證；超出範圍或不符合條件的 AI 回應不會改動存檔。

### O3 — 地區狀態與介面同步

狀態：已補強並實作 O10；AI 明確移動意圖及舊格式回應經同一個相鄰地圖驗證流程套用，HUD、對話提示和存檔保持同步。

- 將 `currentMapId` 作為唯一目前地區來源；AI 只能提出明確的 `travelRequest`，實際切換由前端依相鄰地圖規則驗證後執行，並同步介面、提供給 AI 的狀態及存檔。
- 驗收：每次地區切換後，HUD 顯示位置、附近地點和 AI 行動脈絡一致；非法地區或不連通移動不會造成畫面與存檔不一致。

### O4 — 玩家與敵方行動都進行擲骰

狀態：已實作本地回合制攻防；玩家攻擊與敵方反擊分別顯示 d20 檢定及傷害結算。

- 戰鬥按回合拆解雙方行動：玩家發動攻擊時顯示攻擊檢定；敵方反擊時依玩家能力觸發閃避或防禦檢定。
- 每次攻防都分別呈現骰數、骰面、能力修正、目標值、成功/失敗和對應結果，不讓後續連續行動退化成純 AI 敘事。
- 驗收：每個造成或避免戰鬥效果的行動都有可追蹤的檢定與結算；AI 只負責敘事，不能省略擲骰或單方面決定攻防結果。

### O5 — 中斷後恢復遊戲進度

狀態：已完成快照恢復（玩家狀態、地區、戰鬥怪物/血量/回合、任務及最近 100 則對話）；AI 請求完成或失敗後保存一致快照。

- 每次玩家行動完成並收到 AI 回應後，保存可恢復的遊戲快照，包含玩家狀態、目前地區、進行中的戰鬥及回合階段、任務進度與近期對話紀錄。
- 重新進入遊戲時，優先載入最近一次完整快照，恢復到一致的地區和戰鬥情境；若快照損壞或版本過舊，安全退回有效存檔並提示玩家。
- 驗收：重新載入頁面或中斷後，玩家看到的地區、戰鬥狀態、任務及對話上下文與最後完成回合一致；未完成或失敗的 AI 請求不會留下半套狀態。

### O6 — 完成任務時交付需求道具

### 世界永久改變與分支主線（O28–O39 設計總覽）

狀態：規劃中；以下 O28–O40 為同一設計的分階段實作。建議順序：O15 最小版本 → O28 → O37 → O29 → O38 → O30 → O39 → O31–O35 → O40；O36 驗證器與建置工具可隨時並行；O40 第 1、2 階段只依賴 O38，可提前並行；O41 奪取與靈魂值建議在 O31 之後與 O40 第 1 階段一起進行。整體定位接近《柏德之門》：d20 規則、陣營、具後果的選擇、有盤算的角色與同伴，劇情文本由 AI 依撰寫者提供的骨架生成。

設計原則：

- **單位一致**：玩家、NPC、魔物使用同一套單位模型（種族 × 職階 × 等級／經驗），種類差異只由掛載的功能（對話、商店、掉落、AI 行為）與當前關係表達。
- **規則寫死、內容生成**：任務類型、獎勵上限、事件效果、觸發條件與數值公式由前端資料/規則定義；AI 只在合法候選內選擇、填參數與敘事，前端驗證後才套用。
- **世界在存檔內永久改變**：所有世界變動只經由「事件」入口套用並寫入事件紀錄；AI 不能直接修改世界狀態。
- **主線可分支但永不卡死**：主線改變走向是允許的，無法前進則不允許；主線依賴的任何事物都必須有「非單位、不可摧毀」的替代來源。
- **世界推進由規則執行、AI 只負責可見部分的敘事**：效能成本主要在 AI 呼叫次數與上下文，不在前端運算。
- **引擎與劇本分離**：程式碼不得出現任何具體內容 ID 或名稱（地圖、角色、物品、任務、種族、職階等）；所有劇情、世界觀與內容專屬規則都放在資料中。職階或種族的特殊效果以資料欄位表達（例如職階資料的 `checkBonus: { cha: 2 }`），不得在程式中寫 `if (classId === 'envoy')`。更換整套劇情時只需替換劇本資料，核心玩法與邏輯不變。
- **撰寫者寫骨架，AI 寫血肉**：世界設定、角色卡與關鍵場面要求由人撰寫並驗證；AI 負責銜接、日常對話與依玩家選擇的即時呈現。
- **只有重要角色由 AI 決策**：具名角色可依自身目標、個性與已知資訊做出決策；一般單位使用規則行為；所有 AI 決策都有規則後備。

- 驗收：超出上限、引用不存在單位/物品或發布者不持有的獎勵之提議會被拒絕；獎勵不會被憑空生成或重複發放；發布者死亡時任務依世界規則失敗或轉交。

- 重要角色掛載 `agent` 功能：`goals`（目標/盤算）、`traits`（個性，可搭配九大陣營）、`memory`（與自身相關的重要事件及對玩家印象，設上限並壓縮舊記憶為摘要）、`knowledge`（已知事件）、`ruleFallback`（規則後備行為）。
- **知識範圍**：角色只能依其已知事件決策（親眼目睹、聽聞、同陣營傳遞），事件紀錄需能查詢「誰知道此事件」；送給 AI 的上下文只包含該角色已知部分，不提供全知世界狀態。
- **合法行動清單**：移動、交易、攻擊、結盟、發布任務（沿用 O30 驗證）、招募、逃跑、搬遷等；每個行動具前置條件與冷卻，AI 只能從清單選擇，前端驗證後套用，影響世界的結果以事件寫入紀錄。
- **決策時機**：遊戲時間每日一次、發生與該角色相關的事件、與玩家互動結束後；同一時間點的多名角色合併為一次 AI 呼叫，以控制使用玩家 API Key 的成本。
- **跨多日的行動**：單一行動（例如連續等待、長途移動）跨越多天時，只有最後一天呼叫 AI 決策，之前的天數一律以規則後備行為補算，避免一次行動觸發多次 AI 呼叫。
- **輸出格式**：`{ unitId, action, params, intent }`；每次決策最多一個行動，`intent` 以一句話記錄動機並寫入事件紀錄，供主持人 AI 透過傳聞、對話伏筆或現場結果鋪陳。
- **規則後備**：AI 未被呼叫、失敗或回應無效時改用 `ruleFallback`；遠離玩家的地區延後補算與 O33 模擬測試一律使用規則行為，不呼叫 AI。
- **死亡與繼承**：角色死亡即停止決策；未完成目標依規則交由繼承者（家人、副手或同陣營同職階單位），與主線給予者接手規則一致。
- 驗收：AI 只能選擇合法且前置條件成立的行動；角色決策不引用其未知事件；AI 失敗時世界仍以規則行為推進；玩家不在場的決策可透過事件紀錄追溯並於之後呈現；單次決策的 AI 呼叫數不隨重要角色數量線性增加。

- 同步流程：由專案維護者以腳本將雲端筆記庫複製至 repo `content/`，執行驗證後提交。
- 驗收：寫手不需安裝開發工具即可撰寫並自我驗證；無效參照或缺少必要段落的內容無法進入建置；只有 `final` 內容出現在遊戲中；AI 上下文只包含與當前情境相關的段落。

### O40 — 善惡傾向變化、交易聲望、背叛與傳聞擴散

狀態：規劃中（2026-10-05 由 O38 延後項目整理）。前置：O38；第 3 階段另需 O30、O31，第 4 階段另需 O34 知識範圍。各階段可獨立實作與提交。

共同原則：
- 規則與數值放在劇本資料（例如 `factions.json` 的規則區塊或新增的規則檔），程式不寫死任何勢力、陣營或內容 ID。
- 所有變化都經由事件入口寫入事件紀錄，只影響得知該事件的單位與勢力；例行變化合併記錄，避免淹沒事件紀錄。
- 不增加 AI 呼叫次數：結算由前端規則完成，AI 只在上下文看到結果並據以敘事。

1. **玩家陣營傾向隨行為變化**（只需 O38）
   - 角色存檔新增兩軸傾向分數（善惡、守序／混亂），角色建立時依所選九大陣營給初始值；HUD 與 AI 上下文顯示的陣營名稱由分數依門檻換算。
   - 行為對應的分數變化由資料定義，例如：殺害非敵對單位、殺害無戰鬥能力的 NPC、偷竊（`npcItemTransfers` 中非贈與的取得）、完成委託、放過投降的敵人。自衛（對方先敵對）不扣善惡分。
   - 分數變化本身不寫入事件紀錄，只有陣營名稱改變時寫入一筆事件（傳播範圍為目擊者）。
   - 勢力可在資料中設定重視的價值觀（例如守序勢力對混亂行為額外扣聲望），與 O38 的聲望規則疊加。
   - 翻轉規則（2026-10-06 決議）：傾向可以一路變化到完全翻轉，但以階段性變化為主。
     - 一般行為每次只加減少量分數，單一事件最多讓每一軸跨越一個門檻（例如善良→中立，不會直接善良→邪惡）；超出的分數捨去，不累積到下一次。
     - 只有資料標記為「轉折」（例如 `alignmentShift: { major: true }`）的極少數重大事件，才能在單一事件中跨越多個門檻或直接翻轉；這類事件由寫手在事件或劇情片段資料中明確標示，資料驗證限制其數量並要求附上理由。
     - 同一軸每個遊戲日的變化設上限，避免短時間內重複同一行為快速翻轉（轉折事件不受此限）。
     - 驗收另加：一般行為無論分數多大都只移動一個階段；轉折事件可直接翻轉並寫入事件紀錄；單日上限生效。
   - 驗收：同一行為在不同情境（自衛／主動）得到不同結果；陣營名稱只在跨過門檻時改變並留下紀錄；存讀檔後分數一致；建立角色時選的陣營仍是起點。
2. **交易影響聲望**（只需 O38）
   - 向某勢力成員消費可小幅提高該勢力聲望；以「淨消費金額」計算（購買減去賣回），避免反覆買賣刷聲望。
   - 每個勢力每個遊戲日有聲望上限，且只能從中立提升到友好，不能靠交易達到崇敬。
   - 每個遊戲日每個勢力最多合併寫入一筆聲望事件（地區延後結算時一併處理），不逐筆寫入。
   - 驗收：反覆買賣同一物品不增加聲望；單日上限生效；等待推進時間不會讓上限重置而無限累積（沿用 O29 防刷規則）。
3. **背叛機制**（需 O30、O31）
   - 背叛的定義由資料提供，例如：接下某勢力的委託後把任務物品交給敵對勢力、在劇情片段中出賣盟友、攻擊同盟勢力的成員。
   - 背叛事件造成大幅聲望下降，並在角色存檔留下「背叛過的勢力」紀錄；被背叛勢力的同盟勢力得知時也會下降（比例由資料定義）。
   - 背叛紀錄可作為劇情片段、事件與任務範本的條件（沿用 `matchesFactionConditions` 擴充）；新角色接續時不繼承背叛紀錄，除非選擇與前角色有關聯。
   - 驗收：背叛只能由資料定義的行為觸發；只有得知的勢力受影響；背叛紀錄隨存檔恢復並可被條件查詢。
4. **傳聞隨時間擴散**（需 O34 知識範圍）
   - 事件被一個勢力得知後，經過資料設定的天數，擴散到與其友好、同盟或有貿易往來的勢力，以及相鄰地區的勢力；擴散以新的「傳聞」事件記錄（引用原事件），原事件保持只增不改。
   - 傳聞是否帶有兇手等細節，取決於最初得知的勢力是否知道細節；二手傳聞的聲望影響打折（比例由資料定義）。
   - 擴散在每日結算時以規則處理，設每日擴散數量上限，不呼叫 AI；跨多日的行動一次補算。
   - 驗收：無人目擊的事件不會憑空擴散出兇手；擴散有延遲與上限；重要角色決策（O34）只會看到已擴散到其勢力的事件。

### O41 — 奪取與靈魂值

狀態：待辦（2026-10-06 依寫手新大綱建立）。前置：O28、O29、O38（已完成）；種族分類（LORE-003 待決定第 7 點：哪些是魔族、哪些是智慧生物、感應高低）；態度判定與 O40 第 1 階段一起設計；隱藏結局需 O31、O33。

優先度建議：核心機制（奪取、靈魂值、頭目強化、態度影響）排在 O31 之後，和 O40 第 1 階段（善惡傾向）一起做，因為兩者都會改單位對玩家的態度判定，分開做會改兩次；結局判定隨 O33。若寫手希望先體驗奪取的手感，核心機制只依賴已完成的系統，也可以提前到 O31 之前。

- **奪取動作**：擊倒智慧生物時可選擇「奪取」，以檢定決定成敗。可奪取的對象由資料決定（種族的智慧、魔族分類），刻印失效前限魔族，由劇情旗標解除限制。選擇奪取時立即自動存檔。
- **靈魂量**：每個單位可被奪取的靈魂量是獨立數值（種族基礎值 × 個體加成，存於資料），不與擊倒經驗共用公式。
- **結算**：不論成敗，靈魂量 × 2.5 累加到最終頭目的強化值（世界層，以世界修正或專用計數表達）；成功時主角另獲額外經驗值，靈魂量累加到主角的靈魂值（隱藏，角色層）。失敗時敘事提示主角察覺力量流向某處。所有奪取寫入事件紀錄。
- **態度影響**：種族資料加入「靈魂感應」，感應高的種族依主角靈魂值降低態度；魔族依靈魂值提高「挑戰」或「交易」傾向。與善惡傾向的關係：建議兩者分開記錄、在態度判定時依種族選擇權重（一般種族看善惡、感應高或魔力親和的種族看靈魂值），類似《柏德之門 3》的蝌蚪感染程度；最終是否混合由寫手決定。
- **外顯表現**：靈魂值達門檻時，給 AI 的玩家描述加入可感知的異樣（黑氣、氣味、壓迫感等，候選待寫手決定），只給感應高的人物察覺。
- **結局**：隱藏結局條件為靈魂值達門檻且成功奪取魔王；其餘結局如何受靈魂值影響待三幕與結局設計（O31、O33）。
- 驗收：只有符合條件的對象可被奪取；失敗也會強化最終頭目；靈魂值與頭目強化隨存檔保存；不同感應的種族對同一靈魂值反應不同；選擇奪取後無法以讀檔反悔。

### O42 — 非同步多人（構想）

狀態：構想，優先度極低。前置：O41、正式部署與伺服器端儲存。

- 停用的「新角色接續」系統（歷代角色、事蹟、死亡事件、目擊者與傳聞層級）正好是其他玩家角色出現在你世界中的資料形狀：可把其他玩家的角色紀錄匯入成「傳說中的冒險者」，讓人物以傳聞或傳說層級提起，或留下遺物。
- 需要的新東西：伺服器端儲存與審核、匯入時的 ID 對應與內容過濾，以及不讓匯入資料改變旗標或主線（沿用「傳聞不得使旗標成立」的原則）。

## 建議里程碑

1. **Alpha 穩定化：** 完成回合錯誤處理、狀態驗證、存檔復原與重設。
2. **可玩垂直切片：** 完成一條任務、一張可探索地圖、至少一場有規則的戰鬥與升級循環。
3. **內容擴充：** 擴充地圖、NPC、任務、道具和怪物，補足資料參照檢查。
4. **公開版本：** 完成部署驗收、使用說明、存檔/API Key 提示與核心流程回歸驗收。

## 不在目前範圍

- 多人連線、帳號系統、雲端同步與伺服器端存檔。
- 專案自行託管或轉售第三方模型服務 API Key。
- 未經玩家操作而自動呼叫付費或有配額限制的外部服務。
